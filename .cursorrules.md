# Hospitality Dashboard — Engineering Rules

## Core Principle

Build the simplest production-quality solution that is easy to understand, test, explain, and defend.

**Correctness > simplicity > maintainability > performance > abstraction.**

Do not overengineer.

---

## 1. Architecture

Respect the existing architecture:

**UI → App Router API → Services → Domain → Infrastructure**

* React components handle presentation and user interaction.
* API routes handle HTTP concerns.
* `lib/services` handles application/data operations.
* `lib/domain` contains business rules and pure domain logic.
* Supabase/integrations remain behind clear boundaries.
* Do not put business logic directly inside UI components or API handlers.
* Do not bypass existing service/domain layers without a concrete reason.
* Keep the application a coherent monolith; do not introduce microservices.

The demo and production modes must continue to share the same UI contract.

---

## 2. TypeScript

* Strict TypeScript.
* Never use `any` unless genuinely unavoidable and documented.
* Prefer `unknown` for external data.
* Avoid unnecessary `as` assertions.
* Types do not replace runtime validation.
* Keep domain types explicit and meaningful.
* Prefer discriminated unions for complex state.
* Do not silence TypeScript errors with `@ts-ignore`.

---

## 3. React / Next.js

* Use functional React components.
* Prefer Server Components by default.
* Use Client Components only when interactivity, browser APIs, or client state require them.
* Keep components small and focused.
* Keep state minimal.
* Derive values instead of storing duplicated state.
* Keep business logic out of presentation components.
* Use stable domain IDs as React keys.
* Avoid unnecessary `useMemo`, `useCallback`, and global state.
* Do not add a state-management library unless the existing architecture genuinely requires it.

---

## 4. Data Boundaries

Treat all external data as untrusted:

* Supabase
* API requests
* Webhooks
* iCal feeds
* URL parameters
* Browser storage
* User input
* Third-party APIs
* OpenAI responses

Use:

**external data → validation → domain model → application state → UI**

Never assume an API response has the shape TypeScript says it has.

---

## 5. Reservations — Critical Business Rule

Reservation correctness is more important than convenience.

**Never allow overlapping reservations for the same room.**

Conflict detection belongs in the domain/service layer, not only in the UI.

The backend must remain authoritative.

Expected behavior:

* Validate reservation input.
* Check for conflicting reservations before creation.
* Return an appropriate conflict response (`409`) when an overlap exists.
* Never rely on the frontend to prevent double-bookings.
* Treat Airbnb, Booking, and Direct reservations as competing sources of inventory.

A UI check is useful for user experience.

A server-side/domain check is mandatory for correctness.

---

## 6. Multi-Channel Sync

Channels:

* Airbnb
* Booking
* Direct

External synchronization must be treated as unreliable.

Account for:

* duplicate events
* delayed events
* malformed payloads
* retries
* conflicting updates
* stale iCal data
* network failures

Prefer idempotent operations where appropriate.

Do not assume webhook delivery happens exactly once or in order.

Do not allow an external event to bypass domain validation.

---

## 7. Webhooks

Webhook endpoints are security boundaries.

For signed webhooks:

1. Receive the raw request.
2. Validate the HMAC signature.
3. Use timing-safe comparison.
4. Reject invalid signatures.
5. Validate the payload.
6. Apply domain rules.
7. Trigger synchronization work.

Never trust a webhook merely because it came from a known endpoint.

Never expose webhook secrets to the browser.

---

## 8. Authentication / Authorization / RLS

Supabase Row-Level Security is part of the security model.

* Never rely solely on frontend filtering for tenant isolation.
* Never assume `property_id` filtering in React provides security.
* Authorization must be enforced server-side/database-side.
* Preserve RLS policies.
* Do not bypass RLS casually.
* Service-role credentials are server-only.
* Never expose privileged Supabase credentials to client code.

The frontend can hide data.

**Only the backend/database can enforce access.**

---

## 9. Secrets

Never place privileged credentials in client-side code.

Never expose:

* service-role keys
* OpenAI API keys
* Resend API keys
* webhook HMAC secrets
* cron secrets
* internal API secrets

`NEXT_PUBLIC_*` values are public.

If an operation requires a secret, perform it server-side.

---

## 10. API Routes

API handlers should be thin.

They should primarily:

* authenticate/authorize
* validate input
* call the appropriate service
* translate the result into an HTTP response
* handle expected errors

Do not turn route handlers into giant business-logic files.

Prefer:

**Route → Service → Domain**

over:

**Route → 300 lines of logic**

---

## 11. Async Operations

Every async operation should have a clear lifecycle.

Handle where relevant:

* loading
* success
* empty
* error
* cancellation
* stale responses
* cleanup

For client-side requests:

* avoid duplicate requests
* cancel obsolete fetches with `AbortController`
* prevent stale responses from overwriting newer state
* clean up timers/listeners on unmount

Do not use `useEffect` for calculations that can simply be derived during render.

---

## 12. Search / Filtering / Pagination

Search and filtering should remain predictable.

* Debounce expensive/user-driven searches where appropriate.
* Reset or clamp pagination when filters change.
* Do not duplicate derived filtered data in state.
* Use stable IDs.
* For small datasets, client-side operations are acceptable.
* For large datasets, move filtering/pagination to the backend.

Do not prematurely optimize.

---

## 13. Demo / Production Parity

The application intentionally supports two modes:

**Demo**

* mock data
* no backend required
* no login

**Production**

* Supabase
* authentication
* RLS
* durable jobs

Both modes should preserve the same UI/domain expectations wherever practical.

Do not create completely separate implementations of the product just to support demo mode.

If changing a data contract, consider both paths.

---

## 14. Error Handling

Errors should be explicit and useful.

Handle:

* validation errors
* authentication/authorization failures
* conflicts
* network failures
* third-party failures
* database failures
* malformed external data

Return safe messages to users.

Do not expose:

* stack traces
* database internals
* secrets
* provider credentials
* sensitive infrastructure details

Do not silently swallow errors.

---

## 15. Security

Assume every boundary can be attacked.

Never use:

* `eval`
* `new Function`
* unsafe HTML injection
* unnecessary `dangerouslySetInnerHTML`
* blindly trusted redirects
* client-side authorization as the security boundary

Be alert to:

* XSS
* CSRF
* broken authorization
* insecure direct object references
* secret exposure
* unsafe URLs
* malicious webhook payloads
* dependency vulnerabilities

---

## 16. AI Features

OpenAI is an application dependency, not an authority.

AI-generated content must be treated as untrusted output.

For concierge/message drafts:

* never expose the API key to the client
* validate inputs
* constrain the prompt/context
* handle provider failure
* never assume generated text is factually correct
* never allow generated content to bypass application permissions

The operator remains responsible for messages sent to guests.

---

## 17. External Integrations

Keep third-party integrations isolated.

Current integrations include:

* Supabase
* Airbnb / Booking synchronization
* iCal
* OpenAI
* Resend
* Google Maps / MapLibre
* export libraries

Do not spread provider-specific logic throughout the application.

Prefer a small integration boundary that can be replaced or tested independently.

---

## 18. Testing

Test business behavior rather than implementation details.

Highest-value tests:

* reservation conflict detection
* reservation creation
* invalid reservation data
* webhook signature validation
* duplicate webhook handling
* authorization boundaries
* filtering/pagination
* guest/message workflows
* critical UI interactions

For pure domain logic, prefer straightforward unit tests.

For important user journeys, use integration/E2E tests where justified.

Do not create tests purely to increase coverage numbers.

---

## 19. Performance

Measure before optimizing.

Priorities:

1. Correct data
2. Fast enough UX
3. Reasonable network usage
4. Simple code

Avoid:

* unnecessary requests
* unnecessary renders
* giant client components
* unnecessarily large payloads
* premature caching
* premature memoization

For genuinely large datasets, prefer server-side filtering/pagination and appropriate database queries.

---

## 20. Accessibility

Accessibility is part of correctness.

* Use semantic HTML.
* Interactive controls must work with keyboard.
* Provide labels and accessible names.
* Maintain visible focus.
* Use appropriate disabled/loading/error states.
* Use ARIA only when semantic HTML is insufficient.

Do not build custom controls when a native HTML control solves the problem well.

---

## 21. UI / Product

The dashboard is an **operator tool**, not a marketing website.

Optimize for:

* information density
* fast scanning
* obvious status
* predictable interactions
* minimal clicks
* clear errors
* useful empty states
* operational confidence

Do not add visual complexity that does not improve the operator's workflow.

The existing UI is bilingual English/Portuguese with a sidebar EN|PT toggle. English is the default when no locale cookie is set. Portuguese (pt-PT) is preserved as a first-class locale. Do not add `next-intl` or locale URL prefixes.

Do not casually replace Portuguese operator copy with English-only strings — keep both dictionaries in sync.

---

## 22. Product Logic

Always ask:

**What happens to the operator and the business if this fails?**

Examples:

* stale reservation → possible double-booking
* wrong occupancy → bad operational decision
* failed message → missed guest communication
* incorrect guest data → poor service
* sync failure → inaccurate availability
* exposed credential → security incident

Prioritize engineering effort according to business impact.

---

## 23. Changes to Existing Code

Before changing code:

1. Understand the existing flow.
2. Identify the correct architectural layer.
3. Make the smallest change that solves the problem.
4. Preserve existing behavior unless intentionally changing it.
5. Check demo and production paths.
6. Run lint/typecheck/build where appropriate.

Do not rewrite working architecture simply because another pattern is fashionable.

---

## 24. AI-Assisted Development

AI is an accelerator, not the architect.

When using AI:

1. Understand the requirement.
2. Define the data contract.
3. Identify the correct layer.
4. Generate the smallest implementation.
5. Read the generated code.
6. Test it.
7. Review security and edge cases.
8. Remove unnecessary complexity.

Never blindly accept generated code.

Never ship code you cannot explain.

A good implementation should look like an engineer made the decisions, with AI helping execute them.

---

## 25. Debugging

Use:

**Reproduce → Isolate → Observe → Hypothesize → Test → Fix → Regression test**

Prefer evidence from:

* browser console
* Network tab
* server logs
* database state
* request/response payloads
* TypeScript/compiler errors

Do not randomly modify code until the problem disappears.

---

## 26. Architecture Decision Rule

Before introducing a new library, abstraction, service, pattern, or infrastructure component, answer:

**What concrete problem does this solve?**

If the answer is unclear, do not introduce it.

Prefer:

* one clear monolith
* clear domain boundaries
* typed APIs
* small services
* pure business logic
* simple data flows

over unnecessary distributed architecture.

---

## 27. Definition of Done

A change is done when:

* The requirement is satisfied.
* The correct architectural layer owns the logic.
* TypeScript remains strict.
* External data is validated.
* Security boundaries are preserved.
* Reservation invariants remain protected.
* Async operations cannot corrupt state.
* Errors are handled.
* Demo mode still works where applicable.
* Critical behavior is tested.
* No unnecessary abstraction was introduced.
* The code can be clearly explained in a code review or interview.

---

# Final Rule

**Build boringly correct software.**

Keep the architecture simple enough to explain on a whiteboard.

Keep the business rules explicit enough to test.

Keep security boundaries obvious.

Keep the UI fast and operational.

Use AI aggressively for velocity, but keep engineering judgment human-owned.

**Simple. Correct. Explicit. Secure. Defensible.**
